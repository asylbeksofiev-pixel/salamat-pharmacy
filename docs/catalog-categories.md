# Разделы каталога, фильтры и сортировка

## Данные

| Что | Где |
| --- | --- |
| Товары (13 347 на 19.11.2026) | `public.pharmacy_products` — `id` (уникальный), `article` (может повторяться), `name`, `image_url` |
| Разделы | существующая таблица `Category` (9 разделов из сида, id и slug не меняются) |
| Раздел товара | `catalog_item_categories` — одна строка на `product_id`, ссылка на `Category.id` |
| Журнал запусков и изменений | `catalog_classification_runs`, `catalog_item_category_changes` (для отката) |
| Ручные исправления | `data/catalog-category-overrides.csv` (`product_id,category_slug,note`) |
| Отчёт для проверки | `data/reports/catalog-classification.csv` (+ `.needs-review.csv`, `.summary.json`) |

Привязка только по `product_id`: артикул повторяется и ключом не служит. Названия, артикулы, фото, цены,
корзины и заявки классификация не трогает. Переведённые названия разделов не используются как ключ: сайт
связывает товар с разделом по `Category.id`, а название берёт на языке страницы (RU/KK из базы, EN — из словаря).

`review_status`:

* `auto` — правило уверено (≥ 0,75), товар показывается в разделе;
* `needs_review` — нужна проверка: товар есть в общем каталоге и поиске, но не в разделах; `category_id` —
  предложение или пусто;
* `confirmed` — проверено человеком; автоматические запуски такие строки **никогда не перезаписывают**.

## Классификатор

`src/lib/catalog-classify.ts`, версия в `CLASSIFIER_VERSION`. Без языковой модели: нормализация названия
(регистр, ё→е, «д/» → «для»), словари (формы выпуска, типы товаров, линейки брендов) и упорядоченные правила
с исключениями. Для каждого товара сохраняются раздел, уверенность, правило (`method`), основание (`reason`)
и статус. Правила не выводят фармакологические свойства или регистрационный статус из названия:

* детские лекарства остаются в «Лекарственных средствах», а не в «Маме и малыше»;
* крем с концентрацией действующего вещества — лекарство, крем дерматокосметического бренда — косметика;
* витамины без признака БАД (слова «БАД» или линейки БАД производителя) уходят на проверку;
* капсулы/пастилки без дозировки, спреи с морской водой, саше без описания — на проверку;
* детское питание — в «Маме и малыше» (по назначению), остальное питание — в «Правильном питании»;
* взрослые прокладки и урологические средства — в «Гигиене».

Результат на текущем каталоге (13 347 товаров): см. `data/reports/catalog-classification.summary.json`.

## Команды

Все команды используют `DATABASE_URL` из окружения. Для Neon берите строку **без пулинга**
(`DATABASE_URL_UNPOOLED` в настройках Vercel) — её же использует сборка для миграций.

```bash
# 1. Схема (новые таблицы и индекс). На Vercel выполняется автоматически при сборке (prisma migrate deploy).
DATABASE_URL="<DATABASE_URL_UNPOOLED>" npx prisma migrate deploy

# 2. Пробный прогон: CSV-отчёт и сводка, в базу ничего не пишется.
DATABASE_URL="<DATABASE_URL_UNPOOLED>" npm run catalog:classify

# 3. Запись. Для не-локальной базы нужен --yes. В конце выводится id запуска и проверка целостности.
DATABASE_URL="<DATABASE_URL_UNPOOLED>" npm run catalog:classify -- --apply --yes

# Проверка: каждый товар учтён ровно один раз, нет «висячих» строк и неверных ссылок на раздел.
DATABASE_URL="<DATABASE_URL_UNPOOLED>" npm run catalog:classify -- --verify

# Откат одного запуска: удаляются созданные им строки, изменённые получают прежние значения.
# Строки, изменённые после запуска (в т. ч. подтверждённые вручную), не трогаются.
DATABASE_URL="<DATABASE_URL_UNPOOLED>" npm run catalog:classify -- --rollback <runId> --yes

# Сверка с выгруженной таблицей категорий (Category.csv: id, slug, nameRu …) — только отчёт, ничего не меняет.
DATABASE_URL="<DATABASE_URL_UNPOOLED>" npm run catalog:classify -- --categories-csv Category.csv

# Без базы: пробный прогон по выгрузке каталога ([{id, article, name}]).
npm run catalog:classify -- --from-json catalog.json
```

Повторный запуск безопасен: неизменившиеся строки не трогаются, ручные подтверждения сохраняются.

### Ручная проверка

1. Откройте `data/reports/catalog-classification.needs-review.csv` (UTF-8, открывается в Excel).
2. Для нужных товаров добавьте строки в `data/catalog-category-overrides.csv`: `product_id,category_slug,note`.
3. Запустите `--apply --yes`: такие строки сохранятся как `confirmed`.

Подтвердить можно и прямо в базе (`UPDATE catalog_item_categories SET category_id = …, review_status = 'confirmed' …`).

## Фильтры и сортировка

Параметры URL (общий валидатор `src/lib/catalog-params.ts` для страниц и `/api/catalog/items`):
`q`, `category` (несколько — повторить параметр; между разделами ИЛИ), `priceMin`, `priceMax`, `hasPrice=1`,
`hasPhoto=1`, `sort`, `page`. Между разными фильтрами — И. Неверные значения отбрасываются, ошибки сервера нет.
Любое изменение фильтра или сортировки возвращает на первую страницу; пагинация сохраняет все условия.

Всё считается в SQL по всему каталогу: выдача, количество, счётчики разделов, пагинация. Значения из URL
передаются только параметрами; варианты ORDER BY — из белого списка; у каждого порядка последний ключ — `id`.

**Цена.** Источник — единая цена сети `pharmacy_products.price` (когда этот столбец появится). Она же на
карточке, в фильтре и в сортировке. Нет цены или цена ≤ 0 — «Цена уточняется», никогда не 0 ₸: без ценового
фильтра такие товары остаются в выдаче, при любом ценовом условии исключаются, в обеих сортировках по цене идут
последними. Пока цен нет, ценовой фильтр и сортировки по цене показаны неактивными с пояснением; после
добавления столбца они включаются сами (кэш списка столбцов — 5 минут).

**Популярность.** Надёжных данных нет: заявки не привязаны к id товаров каталога, и заявка — не продажа.
Сортировка «Сначала популярные» показана недоступной с пояснением. Подключить можно, например, число
подтверждённых выдач по заявкам за 90 дней (нужно хранить `product_id` в позиции заявки) или просмотры
карточек товара — когда такой показатель появится, достаточно добавить его в `orderBy` и
`getCatalogFacts().popularityAvailable`.

Наличие, аптека, бренд, производитель, форма выпуска как фильтры не показаны: в `pharmacy_products` для них нет
структурированных данных.

## Индексы

* `catalog_item_categories`: PK `product_id`, `(category_id, review_status)`, `review_status`, `run_id`.
* `pharmacy_products_name_sort_idx` на `(lower(coalesce(name,'')), id)` — порядок по умолчанию: первая страница
  на копии каталога 46 мс → 0,3 мс. Поиск `LIKE '%…%'` по 13 тыс. строк — около 35 мс; при росте каталога можно
  добавить триграммный индекс (`pg_trgm`).

## Кэш

Страницы каталога динамические (зависят от параметров). `/api/catalog/items` кэшируется на CDN на 60 с
(+ stale-while-revalidate 300 с), поэтому новые разделы и фото появляются в API в течение нескольких минут.
