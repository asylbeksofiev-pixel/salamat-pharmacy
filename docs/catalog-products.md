# Каталог из `public.pharmacy_products`

Сайт показывает ассортимент из таблицы `public.pharmacy_products` в базе Neon (`neondb`, ветка `main`):
`id BIGINT` (первичный ключ), `article TEXT`, `name TEXT` — 13 347 строк, импорт завершён.

* Таблица только читается. Сайт её не изменяет и не обращается к `public.pharmacy_products_import`.
* Уникальный идентификатор товара — `id`. Артикул не уникален: товары с одинаковым артикулом показываются
  отдельными карточками и открываются по своему `id`.
* Цен, остатков, категорий и изображений в таблице нет — на сайте «Цена уточняется» и «Наличие уточняется».
* **Заявка на уточнение.** Кнопка «В корзину» кладёт товар в ту же корзину (`localStorage`, ключ — числовой `id`)
  без цены. `/api/cart/quote` и `/api/orders` распознают числовые id (`isCatalogId`), читают товар из таблицы и
  делают строку «цену и наличие подтвердит аптека» (`kind: "catalog"`, `unitPriceKzt = null`). Такая заявка
  сохраняется в `Order` со статусом «Новая», `totalKzt = null`, `hasUnpricedItems = true`; в `OrderItem`
  `variantId = null`, `nameSnapshot` — название, `skuSnapshot` — артикул SALAMAT (или `#id`, если артикула нет).
  Сотрудники аптеки видят её в админке, как любую заявку. Онлайн-оплаты и доставки нет.
* Корзина и заявки доступны, если в каталоге есть товары и хотя бы одна аптека принимает заявки
  (`Pharmacy.acceptsOrders`); иначе `/cart` и `/checkout` предлагают позвонить в аптеку (`src/server/storefront.ts`).
* На главной — 4 товара из таблицы в стабильном порядке (`listCatalogPreview`: сначала с фото, затем названия,
  начинающиеся с буквы, затем по названию и `id`). Это не «популярные» и не «рекомендуемые» товары.
* Таблица не управляется миграциями Prisma: её не создают, не меняют и не удаляют `prisma migrate deploy` и seed.

## Подключение к базе

Запросы выполняются только на сервере (серверные компоненты Next.js и API-маршруты) через уже настроенный Prisma
Client и переменную `DATABASE_URL` из Vercel — это адрес **пула соединений Neon** (хост с `-pooler`), его
добавила интеграция Neon. Для миграций при сборке используется прямое подключение `DATABASE_URL_UNPOOLED`.
Браузер получает только готовый HTML/JSON: ни адрес базы, ни пароль в клиентские файлы не попадают
(проверяется поиском по `.next/static` и тестом API).

## API

`GET /api/catalog/items?q=парацетамол&page=2&pageSize=24`

```json
{
  "items": [{ "id": "1234", "article": "A-1", "name": "…", "price": null, "stockQuantity": null, "category": null, "imageUrl": null }],
  "total": 37, "page": 2, "pageSize": 24, "pageCount": 2, "query": "парацетамол", "layoutFixed": false
}
```

* `pageSize` — по умолчанию 24, максимум 48; страница за пределами — пустой `items` при верном `total`.
* `id` возвращается строкой (BIGINT безопасно передаётся в JSON и URL).
* Ограничение частоты: 240 запросов в минуту с одного IP на инстанс; ответы кэшируются CDN на 60 с.
* Ошибка базы → `503 {"error":"unavailable"}`, на странице — понятное сообщение и кнопка «Повторить».

## Поиск

* Строка запроса делится на слова (до 8). **Каждое** слово должно встретиться в названии **или** в артикуле.
* Сравнение без учёта регистра, буквы «ё» и «е» равнозначны: `translate(lower(coalesce(name,'')), 'ё', 'е') LIKE $1`.
  Слова передаются параметрами; символы `%`, `_`, `\` экранируются и ищутся буквально.
* Порядок: сначала совпадения с начала названия/артикула, затем по названию, затем по `id`. Благодаря `id` в
  конце сортировка детерминирована — пагинация не повторяет и не пропускает записи.
* Если ничего не найдено, а запрос набран в английской раскладке, поиск повторяется с исправленной раскладкой.
* Всего строк и текущая страница считаются отдельными запросами `COUNT(*)` и `LIMIT/OFFSET`; весь каталог в
  браузер не отправляется.

## Необязательные индексы (не применялись)

Для 13 347 строк поиск полным просмотром таблицы занимает миллисекунды, поэтому база не менялась. Если каталог
вырастет до сотен тысяч строк или поиск станет медленным, выполните в Neon SQL Editor (без блокировки таблицы):

```sql
-- Расширение pg_trgm уже установлено первой миграцией сайта.
CREATE INDEX CONCURRENTLY IF NOT EXISTS pharmacy_products_name_search_trgm
  ON public.pharmacy_products USING gin (translate(lower(coalesce(name, '')), 'ё', 'е') gin_trgm_ops);
CREATE INDEX CONCURRENTLY IF NOT EXISTS pharmacy_products_article_search_trgm
  ON public.pharmacy_products USING gin (translate(lower(coalesce(article, '')), 'ё', 'е') gin_trgm_ops);
```

Выражения в индексах совпадают с выражениями в запросе — только так PostgreSQL сможет использовать индекс для
`LIKE '%…%'`.

## Когда появятся цены, остатки, категории и изображения

Код уже готов: при каждом запросе (с кэшем 5 минут) сервер проверяет, какие из столбцов `price`,
`stock_quantity`, `category`, `image_url` есть в таблице, и выбирает только их. Добавьте столбцы **без значений
по умолчанию**, чтобы не появилось выдуманных данных:

```sql
ALTER TABLE public.pharmacy_products
  ADD COLUMN IF NOT EXISTS price numeric(12, 2),
  ADD COLUMN IF NOT EXISTS stock_quantity integer,
  ADD COLUMN IF NOT EXISTS category text,
  ADD COLUMN IF NOT EXISTS image_url text;
```

После заполнения реальными данными сайт сам покажет цену (только если она больше 0), наличие («Есть в
наличии» / «Нет в наличии»), категорию и фото (только `https://`). Пустые значения по-прежнему выводятся как
«Цена уточняется» / «Наличие уточняется». Общий столбец `price` не относится к конкретной аптеке, поэтому в
корзине и заявке такие товары по-прежнему идут «на уточнение» — подтверждённую цену даёт только выгрузка цен
по аптекам (`Price`).
